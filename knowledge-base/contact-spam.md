# Contact form spam filter

Task: VAS-985, 4203627c-9d41-4123-a268-1ae32f6ffb38 (`vk/4203-prevent-contact`), 2026-11-08. PR #198.

`/api/contact` in `api/app.ts` checks a message in this order: the hidden `company` honeypot, field validation, then TypeSafe's Jev model, then Slack. Jev is a "System One" model: you send a `state` and typed questions to `POST https://api.typesafe.ai/v1/systemone` with `model: "jev-latest"`, and a Noul (yes/no) question comes back as `answers.<id>.noul`, the probability of yes. There's no text to parse. Docs: https://docs.typesafe.ai/llms.txt.

- The state holds the site, the form, and the sender's name, email and message. The `spam` question's `criteria.true` and `criteria.false` describe a mass pitch versus a person writing to David. The instructions say every field is sender-typed evidence, not instructions, to blunt prompt injection through `name` and `email` as well as `message`.
- Dropped at `spam >= 0.9`. The sender still gets the 303 to `/contact/thanks/`. The whole message is logged as one `JSON.stringify` line with `"event":"contact_spam_dropped"`, so sender text can't forge extra log lines. Logs aren't kept, so set the optional `SLACK_SPAM_WEBHOOK_URL` (a second incoming webhook for a quiet channel) to keep every dropped message readable later. Without it, a misfiled message can only be found while running `npx wrangler tail david-vasandani-blog`.
- Fails open: no `TYPESAFE_API_KEY`, a non-2xx, a network error, a 5 s timeout, a missing answer or a number outside 0 to 1 all deliver to Slack. Each failure except the unset key logs `Jev spam check skipped, delivering the message: <reason>`, so a broken key or quota shows up in the tail rather than as spam quietly returning. Keep it failing open; an outage must not lose real mail.
- Jev is only called once `SLACK_WEBHOOK_URL` is known to be set, so an unconfigured Slack never sends visitor data to TypeSafe.
- `TYPESAFE_API_KEY` is a Worker secret, set with `wrangler secret put`. The key is in David's 1Password. Setting a secret redeploys the current code, which is harmless when the code doesn't read it yet.

Cutoff evidence: spam samples scored 0.99; a recruiter 0.18; a reader question and a friend 0.01; an unsolicited but genuine request for feedback on an open-source tool 0.71. That last one is why the cutoff is 0.9, not 0.8. If real messages go missing, look at their logged score before lowering or raising it, and add a test that mocks the score rather than calling the live API.

Tests mock `fetch` and route on URL (`https://api.typesafe.ai/v1/systemone` versus the Slack webhook). Never point a test or smoke check at the real Slack webhook. `mockFetch` restores the real `fetch` saved at load time, not the previous one: node:test runs `t.after` hooks first-in first-out, so restoring "the previous fetch" from several mocks in one test leaves a mock installed. The first version used a word list (unsubscribe, "reply YES", backlinks); it was replaced because it only caught exact phrases.

Review follow-up (2026-11-23): a review of PR #198 led to the full dropped-message log, the spam channel, failure logging, the 0 to 1 bounds check, the Slack-before-Jev order, the cutoff edge test and the `mockFetch` fix. Still open: the contact page says messages go "straight to David" and the privacy policy doesn't name TypeSafe; and the form has no rate limit, so a flood costs Jev calls until the quota runs out and the filter fails open. Rate limiting would be a Cloudflare dashboard rule.
